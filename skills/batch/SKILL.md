# Batch: 大规模并行变更编排

将大型代码变更分解为多个独立、可并行执行的工作单元，逐一实现并提交。

## 适用场景

- 跨多个文件的大规模重构（迁移框架、统一命名）
- 批量添加功能（给所有模块加类型注解、加文档）
- 代码库级别的模式替换（替换 API、更新导入路径）
- 多模块一致性修改（统一错误处理、日志格式）

## 执行流程

### Phase 1: 研究与规划

**1. 理解变更范围**

```bash
# 搜索所有受影响文件
grep -r "旧模式" --include="*.py" -l
find . -name "*.py" | xargs grep -l "目标模式"

# 统计影响规模
grep -r "旧模式" --include="*.py" -l | wc -l
```

**2. 分解为独立工作单元**

将变更分解为 3-20 个独立单元（根据实际规模调整），每个单元必须：
- 可独立完成和测试
- 不依赖其他单元的完成顺序
- 范围明确（具体文件列表）
- 大小均匀（拆分过大的，合并过小的）

推荐按目录或模块切分，而非任意文件列表。

**3. 制定验证策略**

每个单元完成后如何验证：
- 运行单元测试: `python -m pytest tests/ -v`
- 类型检查: `python -m mypy .`
- lint 检查: `python -m ruff check .`
- 导入验证: `python -c "import affected_module"`

**4. 输出计划**

```
## Batch 计划: [变更描述]

### 研究结果
- 影响文件数: N
- 涉及模块: [模块列表]
- 现有约定: [发现的代码模式/约定]

### 工作单元

| # | 标题 | 文件/目录 | 变更描述 |
|---|------|----------|---------|
| 1 | ... | ... | ... |
| 2 | ... | ... | ... |
| ... | | | |

### 验证策略
- 每个单元完成后: [验证步骤]
- 全部完成后: [最终验证]
```

### Phase 2: 逐单元实现

对每个工作单元，按以下步骤执行：

**Step 1: 实现变更**
- 按照计划修改指定文件
- 遵循项目现有代码风格和约定
- 保持变更最小化——只做计划内的修改

**Step 2: 验证**
- 运行相关的测试
- 检查类型/lint 是否通过
- 确认没有影响其他模块

**Step 3: 提交**
```bash
git add <affected-files>
git commit -m "<type>(<scope>): <description>

Part of batch: <overall-task-description>
Unit N/M"
```

### Phase 3: 最终验证与汇总

所有单元完成后：

1. **全量测试** — 运行完整测试套件
2. **一致性检查** — 确认所有单元的风格和模式一致
3. **遗漏检查** — 确认没有遗漏的文件或模式
4. **汇总报告**

```
## Batch 完成报告

### 执行概要
- 计划单元: N
- 完成单元: N
- 总提交数: N
- 修改文件数: N

### 单元状态

| # | 标题 | 状态 | 提交 |
|---|------|------|------|
| 1 | ... | ✅ done | abc123 |
| 2 | ... | ✅ done | def456 |
| ... | | | |

### 验证结果
- 测试套件: ✅ 通过
- 类型检查: ✅ 通过
- Lint: ✅ 通过

### 总结
[一句话总结]
```

## 注意事项

1. **先规划后执行** — 不要跳过 Phase 1 直接开始改代码
2. **保持独立** — 每个单元必须可独立合并，不依赖其他单元先落地
3. **小步提交** — 每个单元一个 commit，方便 review 和回滚
4. **遵循约定** — 保持一致的代码风格，不要让每个单元看起来像不同人写的
5. **验证每个单元** — 不要等全部完成再测试，边做边验证
